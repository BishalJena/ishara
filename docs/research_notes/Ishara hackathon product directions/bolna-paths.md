# Bolna integration paths for a compelling Ishara hackathon entry

Research date: 18 October 2026. Research only: Context7 resolve/query, Exa discovery/fetch, direct inspection of original public source. No installation, inference, session creation, calls, key reads or account changes. User now confirms meaningful Bolna integration is mandatory and explicitly permits evaluating deviations when the preferred workflow is weak. Ordinary own-number calls remain the preferred experience; service-originated alternatives below are clearly identified pivots. Hosted-only versus open-source integration eligibility remains unestablished; that does not make the source path technically impossible.

## 1. Can Bolna accept externally recognized signing and return speech without originating a telephone call?

### Takeaway

**Yes at the open-source framework/extension level; not established as a ready hosted speech API.** Bolna has a real non-telephony WebSocket transport with text input, base64 audio output, playback marks and clear messages. Source inspection also exposes several defects and assumptions that make it unsafe to describe text-to-voice as configuration-only. [Framework](https://github.com/bolna-ai/bolna), [input source snapshot](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/input_handlers/default.py), [output source snapshot](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/output_handlers/default.py)

### Cited Findings

- The repository distinguishes the OSS orchestration framework from closed-source hosted APIs and playground. README explicitly supports programmatic agents without the local telephony setup; provider credentials are separately required. The license permits modification/distribution with copyright/license notice retained. This is evidence for engineering an adapter, not proof that a hosted Bolna key buys standalone synthesis or all provider inference. [README](https://github.com/bolna-ai/bolna/blob/master/README.md), [MIT license](https://github.com/bolna-ai/bolna/blob/master/LICENSE)
- The example server exposes `/chat/v1/{agent_id}` as a WebSocket, accepts it and constructs `AssistantManager(agent_config, websocket, agent_id)` before running the pipeline. This is a server/source integration route independent of PSTN. The example shown lacks user authorization on that route and agent CRUD: use it as an implementation reference, not a production deployment configuration. [Quickstart server](https://github.com/bolna-ai/bolna/blob/master/local_setup/quickstart_server.py)
- `DefaultInputHandler.process_message` accepts `type` values audio, text, mark and init. Text packets are `{ "type": "text", "data": "approved utterance" }`, then `__process_text` places them in the **LLM queue**, not the synthesizer queue. A claim that any text goes straight to voice is false for the inspected implementation. [Pinned input handler](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/input_handlers/default.py)
- That text function selects `self.input_types["audio"]`. The utility creates separate text routes when a pipeline starts with LLM/synthesizer, so a text-only configuration can raise KeyError and a mixed pipeline can take the wrong route. The code observation is independently documented in open issue #898. No execution was performed here. [Input snapshot](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/input_handlers/default.py), [utility](https://github.com/bolna-ai/bolna/blob/master/bolna/helpers/utils.py), [issue 898](https://github.com/bolna-ai/bolna/issues/898)
- In inspected `TaskManager.run`, `_listen_llm_input_queue()` is started for `turn_based_conversation`, while synthesizer listening is started when **not** turn-based. Text input explicitly sets `bypass_synth` when turn-based. `textual_chat_agent` is initialized false and an apparent detection branch sets it false again. These are additional lifecycle assumptions that must be addressed in a mixed text/audio interpreter; changing only the one wrong dictionary key is not enough evidence of a working full path. [Pinned task manager](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/agent_manager/task_manager.py)
- The convenience `Assistant.add_task` accepts input/output queues but `execute()` constructs the manager with queues set to None; its textual/no-transcriber pipeline construction does not establish a working direct text+synthesizer application. Prefer the lower-level manager and explicit transport inspection over assuming README pseudousage is a live streaming implementation. [Assistant source](https://github.com/bolna-ai/bolna/blob/master/bolna/assistant.py), [manager](https://github.com/bolna-ai/bolna/blob/master/bolna/agent_manager/assistant_manager.py)
- `DefaultOutputHandler` encodes generated bytes as base64 in `{data,type:"audio"}`, sends pre/post `mark` identifiers, and `handle_interruption()` sends `{data:null,type:"clear"}` and clears mark state. The input handler consumes returned mark acknowledgments and accumulates corresponding text as heard. These are useful real primitives for delivery/cancellation; a client still must implement playback/clear and ACK only after playback, and an ACK is application evidence rather than proof a human comprehended it. [Pinned output](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/output_handlers/default.py), [pinned input](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/input_handlers/default.py)
- Hosted Custom TTS is the developer's upstream `/audio/speech` server called **by Bolna**; it is not an independently callable hosted Bolna synthesis endpoint. Previous bounded not-found finding remains accurate for the hosted interface, but must not be generalized to the OSS framework. [Custom TTS](https://www.bolna.ai/docs/custom-tts.md)
- Current hosted Web Call SDK v3 connects a browser directly to a Bolna agent, and requires account enablement on request. Public API has start/stop/mute/run ID and audio element but no sendText or transcript event. Source confirms mandatory mic preflight via `getUserMedia`, followed by SIP.js capture. However its `attachRemoteAudio()` obtains receiver tracks, forms a MediaStream, and assigns `audioElement.srcObject`: output is not intrinsically locked inside a black box. A custom audio element exposes that remote stream to normal browser media processing; no raw PCM callback or Phone AAC route is supplied. [SDK guide](https://www.bolna.ai/docs/developer-resources/sdks/web-call.md), [API](https://www.bolna.ai/docs/developer-resources/sdks/web-call-api.md), [source snapshot](https://github.com/bolna-ai/web-call/blob/e3ad5207fce6f03b44ba74125142d42f457bea7f/src/call.ts), [types](https://github.com/bolna-ai/web-call/blob/e3ad5207fce6f03b44ba74125142d42f457bea7f/src/types.ts)
- Source discovery caution: Exa's GitHub repository summary still said latest v1.0.4 in 2025, but the live GitHub tree API exposed v3-era TypeScript sources and distributions. We followed the actual tree and source rather than accepting the stale summary. Separately, raw master and API-returned commit snapshots differed, so source claims above are pinned to inspected snapshots instead of asserting a single current master state. [Tree](https://api.github.com/repos/bolna-ai/web-call/git/trees/main?recursive=1), [Bolna commit API](https://api.github.com/repos/bolna-ai/bolna/commits/master)

### Inferences

- An engineerable native sidecar is **recognized user-approved text → custom Bolna text transport → deterministic pass-through or faithful bounded wording policy → Bolna synthesis/stream ordering → native audio consumer → Apple AAC injection**. Recognition remains external. This is a source extension requiring a fork/adapter and device proof, not an API flag. Clear packets/sequence IDs can cancel not-yet-played audio; already heard speech cannot be retracted. [Source primitives](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/output_handlers/default.py)
- No invented recipient context: a sidecar cannot obtain the incoming native Phone transcript merely by receiving Bolna audio. Bolna can manage approved outbound delivery and voice but cannot interpret a clinic's unseen offer or autonomously confirm it. Broader assistant reasoning would create false confidence.
- For an in-person version, the app owns the microphone and camera, so a transport extension can send hearing-person speech through Bolna's ASR and return captions, while signing feeds the outgoing speech path. Bolna can then own **bidirectional media orchestration, ASR provider selection, voice/language, turn boundaries, playback ordering, cancellation and pause policy**. That is more than a TTS wrapper if implemented demonstrably; using only its synthesizer class is a thin integration. ASR-to-app output requires a hook/tee: the normal task manager's terminal transcript branch only logs that output needs separation, rather than providing an established caption event. [Task manager](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/agent_manager/task_manager.py)

### Gaps

- No runtime validation, text pipeline patch, provider inference, native AAC stream test, caption tee, cancellation latency or mobile SDK adaptation was executed.
- Hosted-only sponsor requirement and whether self-hosted source contribution qualifies are unknown; meaningful technical integration does not automatically prove event eligibility.
- Do not promise a one-line upgrade, public direct TTS API, receive-only SDK flag or a standard media bridge from browser audio to native Phone.

## 2. Can hosted Bolna be central to a user-controlled signing conversation or everyday task?

### Takeaway

**Yes: hosted call orchestration plus external app events/custom tools is a strong fit.** It most naturally carries the hearing person's call itself, which changes caller identity from the preferred own-SIM call. A bounded signing-led errand or a user-controlled relay avoids the unsupported audio ownership of an unrelated Phone call and gives Bolna substantive responsibilities. [Outbound](https://www.bolna.ai/docs/outbound/making-calls.md), [events](https://www.bolna.ai/docs/graph-agent/event-injection.md), [tools](https://www.bolna.ai/docs/graph-agent/tools-and-rag.md)

### Cited Findings

- Hosted graph events `POST /v1/call/{run_id}/events` merge properties into context and can transition nodes plus initiate proactive speech. This enables a signing app to affect an ongoing conversation without faking microphone speech. It is not just a static greeting integration. [Events](https://www.bolna.ai/docs/graph-agent/event-injection.md)
- Graph custom HTTP tools call an external endpoint with structured parameters. Tools can be node-scoped; function_call forces the response LLM's tool choice but does not bypass generation and auto-invoke a function. This supports publishing an offered time/status to an app and separating collect/approval/confirm phases. [Tools](https://www.bolna.ai/docs/graph-agent/tools-and-rag.md)
- Graph event transitions coexist with speech and expression edges. Events are buffered while speaking or generating. If recipient speech is in progress, transition occurs but proactive speech may be skipped; a 202 means event publication, not audible delivery. Thus user approval must be stored durably and relevant to a current offer, and delivery/retry needs validation. [Events](https://www.bolna.ai/docs/graph-agent/event-injection.md)
- Custom LLM endpoints receive OpenAI Chat Completions messages and return streamed deltas, and get called for conversation, routing, voicemail and ending checks. The app can implement a deterministic conversation adapter for exact user-approved words while treating other tasks separately. Prompt-only 'repeat exactly' is weaker than deterministic output; endpoint task discrimination and session correlation need wire proof. [Custom LLM](https://www.bolna.ai/docs/customizations/using-custom-llm.md)
- Bolna has genuine appointment tool integrations: Cal.com can check availability and book after confirmation. This is only usable when the business has connected its calendar; it does not magically query or book an arbitrary local clinic's calendar. A call to a staffed business can instead negotiate verbally and record the human's stated confirmation. [Booking example](https://www.bolna.ai/docs/tool-calling/book-calendar-slots)
- Engine user detection, hangup-on-silence and total timeout are configurable. Normal voice-agent silence recommendations are too short to assume suitable for a signer reading an offer and responding. Online prompts and hangup policy must be designed for signing pauses. [Engine](https://www.bolna.ai/docs/agent-setup/engine-tab.md)
- Graph nodes can disable general LLM hangup decisions and explicitly end at chosen closing nodes. This supports controlled phases, though a graph prompt alone cannot enforce all user-consent policies. [Tools/end-call settings](https://www.bolna.ai/docs/graph-agent/tools-and-rag.md)

### Inferences

- **Controlled live relay:** user selects contact and starts a call in Ishara; Bolna originates the hearing leg; signed approved messages drive speech; turn transcripts or structured offers are sent to the app; signer chooses the reply. Bolna handles the actual remote audio, ASR/TTS, pauses, interruption and lifecycle. This is ordinary interaction for the recipient and a familiar contact/Call/sign/read pattern for the user, but **not an ordinary own-number native cellular call**. Must disclose that deviation honestly.
- **Supervised errand:** user signs 'ask courier to leave package at reception' or 'ask repair shop if my phone is ready', approves the interpreted request, and Bolna makes the call. Bolna can ask factual clarifications, report alternatives, and wait for a signed/tapped decision before a commitment. This reduces vocabulary and continuous recognition pressure while providing real end-to-end voice-agent value. It changes the task from 'speak every word for me' to 'carry out my approved request'; do not pretend these are the same product.
- A strong supervised demo is a changed offer: repair shop says 'ready after 6, not 4'; app shows the actual offer; user signs a supported alternative/approval; Bolna communicates it and obtains confirmation. The visible authorization step proves user agency better than an autonomous fake-signing agent. This proposed demo is not validated user demand.
- A structured offer HTTP tool is a credible alternative to promising live word-by-word captions. It must be labeled as an interpreted offer, include uncertainty, and avoid displaying a booking confirmation until the business actually states it. The custom-LLM adapter is a candidate source of turn text, not an established partial-ASR stream API.

### Gaps

- Still untested: hosted call feature enablement, custom-LLM payload correlation/task markers, actual turn transcript delivery latency, event re-entry, exact speech/cancellation, long-pause handling, retry/duplicate behavior and verified caller identity.
- No real business or number was called. Provider verification/credits are operational prerequisites only for an explicitly selected and authorized service-originated experiment.
- No business integration is assumed. Calendar tooling is optional demo infrastructure, not a dependency imposed on every local clinic/shop.

## 3. Which three paths should the team rank for a winning, genuinely Bolna-powered demonstration?

### Takeaway

**Rank a hosted controlled call first for fidelity to the communication vision; rank a bounded supervised errand second for feasibility and depth; keep native own-number OSS injection third as a distinct higher-risk track.** An in-person service-counter implementation is a meaningful alternative to the third track when native audio constraints dominate; it should use the same real orchestration responsibilities rather than rename ordinary TTS as Bolna integration.

### Cited Findings

| --- | --- | --- | --- |
| **1. Ishara accessible calling with user control** | Carries hearing person's call; remote ASR, signed-message TTS, interruption and pause policy, graph/tool turns, call lifecycle. Removing Bolna removes the working call medium. | Contact → Call in Ishara → sign/read → approve offer → finish. Recipient answers normal phone. **Service-originated caller identity; replaces native call origination.** | Existing hosted call, custom LLM, tools/events are documented. Dynamic exact speech, app transcript/offer delivery, event overlap and signing pauses need empirical proof. ### Inferences

- Best technical next decision is an **interface proof**, not another model comparison: can one user-approved utterance produce exact audible speech; can one actual recipient offer reach the app; can one explicit user choice change the active call without autonomous commitment? This validates meaningful Bolna integration and the demonstration's central human outcome together.
- For native sidecar, the sponsor claim should be restrained: Bolna streaming/cancellation orchestration is real, but ordinary TTS alone is replaceable. To be compelling, show its handling of interrupted speech, deliberate signing pauses, selectable Indian-language voices and a transparent delivery state. Do not bolt on an agent that guesses the signer's intent simply to increase Bolna surface area.
- For in-person counter, app owns media so orchestration can genuinely cover both directions. A noisy/no-private-space demo and camera framing remain important product questions. A specialized service desk workflow is more credible than universal live sign translation if only bounded signs are supported.
- No ranking predicts a win. The strongest submission should show a task completed with a changed offer or correction, source and runtime evidence, bounded honest language coverage, and user agency. Recognition accuracy and Deaf/ISL review remain separate risks not solved by Bolna.

### Gaps

- No evidence establishes judge weights, a win probability, Deaf user acceptance of any pivot, or sufficiency of OSS usage for this specific event. User-confirmed mandatory Bolna integration is controlling; do not re-open that question or tell the founder to do the technical investigation.
- Do not present these ranked alternatives as an approved architecture or authorization to build. The user asked for research and ideas; implementation remains paused.
