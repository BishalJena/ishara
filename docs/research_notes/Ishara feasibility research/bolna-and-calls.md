# Bolna and native cellular calls: Ishara feasibility research

Research date: **18 October 2026**. Evidence: current original Bolna Markdown docs and index, Context7 `/websites/bolna_ai` resolve/query, Exa search/fetch, and three authenticated read-only GET requests. **No product code, installation, agent creation, deployment, outbound call, synthesized audio, model inference, or paid-service action was executed.** No key, email, telephone value or account/agent ID is recorded here.

**The user clarified a hard requirement during research:** they place an ordinary cellular Phone call **from their own existing number directly to the clinic**, with Ishara speech injected into that existing call. Bolna-originated PSTN, calling Bolna first, callback, or a second service-to-clinic bridge **does not meet the requirement**. Earlier service-originated designs below are superseded; retained source details must not be used to recommend a different workflow. A verified Bolna destination is **not required** for this native call path.

Labels: **D** documentation-supported; **I** engineering inference; **G** unresolved; **E** directly executed observation. Apple/AAC, native Phone audio ownership, camera and system-caption details are covered by the separate iOS research. No Bolna feature should be treated as bypassing those boundaries.

## 1. Bolna as non-telephony speech processing for the existing Phone call

### Takeaway

**No publicly documented standalone Bolna arbitrary-text-to-audio synthesis endpoint was established.** Bolna Custom TTS's `/audio/speech` is **YOUR server's endpoint that Bolna calls**, not `api.bolna.ai/audio/speech` that Ishara can call. Voice APIs list voices/providers; they do not generate audio. This is a bounded documentation finding, not proof that no private/beta service exists. [Custom TTS](https://www.bolna.ai/docs/custom-tts.md), [Voice APIs](https://www.bolna.ai/docs/api-reference/voice/overview)

The browser WebRTC SDK avoids PSTN, but creates a browser-to-agent audio session and requests microphone access. Receiving that audio in the background and injecting it through Apple's supported app-speech mechanism is an **engineering hypothesis** requiring audio-route, microphone, exact-trigger and background checks. It is not a documented native Phone integration. [SDK guide](https://www.bolna.ai/docs/developer-resources/sdks/web-call.md), [SDK reference](https://www.bolna.ai/docs/developer-resources/sdks/web-call-api.md)

### Inferences preserving the hard requirement

1. **Native speech first:** Recognition/decision → approved text → Apple's supported app speech injection into the existing Phone call. Validate local speech first to isolate platform media behavior. Any cloud TTS audio path still needs specific Apple routing proof. Bolna has no established mandatory role yet. [Documented Bolna scope](https://www.bolna.ai/docs/developer-resources/overview.md)
2. **Bolna WebRTC only as an audio source:** Potentially retain a non-PSTN session, trigger exact app-supplied text, obtain agent audio and inject it natively. Required proof: receive-only or non-conflicting microphone handling, session embedding, text trigger, exact generation, usable audio output, foreground/background survival and Phone coexistence. The session must never call the clinic. [SDK](https://www.bolna.ai/docs/developer-resources/sdks/web-call-api.md), [events](https://www.bolna.ai/docs/graph-agent/event-injection.md)
3. **Direct underlying TTS:** A standalone provider could return approved-text audio with less agent orchestration, preserving the call. This reduces Bolna participation and needs separate provider docs/access/cost/audio-route evaluation. A Bolna key is not a direct provider key. [Bolna's upstream provider list](https://www.bolna.ai/docs/text-to-speech.md)

NativePhone AAC plus **system-visible captions** is the current research candidate, pending device proof. System captions visible to the user are not automatically text accessible to Ishara; do not market app-owned caption access based on visibility. A Bolna session has no automatic access to native call audio.

### Gaps and narrowly scoped vendor questions

- Is there supported standalone HTTP/streamed text-to-audio synthesis, independent of an agent call/session? Exact URL, formats, account flags and price?
- Can WebRTC/native transport be receive-only without microphone permission/input audio-session ownership? Can audio be obtained as buffers/MediaStream rather than only played in a browser element?
- Is there a current exact-text speech API, audio-only session or native iOS SDK? Does it explicitly support coexistence with Phone's cellular audio session?
- A feature-request answer would improve plausibility but still not demonstrate iPhone17 behavior.

**Bounded not-found search:** current llms index, TTS overview, Custom TTS, Voice APIs, calling API overview, developer resources, deployment guide, current SDK guide/reference, Custom LLM and graph event/static-node pages. Exa queries for original standalone/non-call synthesis docs returned agent/provider/configuration pages, not a direct Bolna audio-generation API. [Index inspected](https://www.bolna.ai/docs/llms.txt)

## 2. Archived service-originated path: useful source facts, explicitly rejected workflow

**Read this section only as feature evidence and correction history.** All suggestions to originate the user's call through Bolna or wait for a verified Bolna destination are superseded by the explicit native-call requirement. ### Archived service-originated relay findings: not the required workflow

#### Takeaway (service-agent path only)

**D/I:** Bolna has credible building blocks for an app-controlled relay: streamed custom Chat Completions output feeds TTS, and REST events can initiate graph-agent speech without the telephone recipient speaking first. These are not a demonstrated arbitrary-text `speak()` API. An adapter and an empirical validation remain necessary. [Custom LLM](https://www.bolna.ai/docs/customizations/using-custom-llm.md), [event injection](https://www.bolna.ai/docs/graph-agent/event-injection.md)

#### Inferences (superseded proposals, not recommendations): candidate relay designs, not an architecture decision

1. **Short completed custom-LLM requests + event trigger:** Forward each receptionist turn to Ishara as a finalized caption, finish that response cycle, wait outside any Bolna generation, and issue an event when the signer has a sentence ready. The custom endpoint then emits the pending exact sentence as delta content. This combines the documented custom output protocol and event transition mechanism, but empty/no-speech replies, correct triggering, context binding, graph custom-provider support, and repeated utterances require proof. [Underlying protocols](https://www.bolna.ai/docs/customizations/using-custom-llm.md), [event constraints](https://www.bolna.ai/docs/graph-agent/event-injection.md)
2. **Long-held custom-LLM request:** Receive a receptionist turn, publish it to the app, and wait for the signer before returning text. This is the conceptually simplest coupling but the most timeout-sensitive. **Do not select it merely because SSE can remain open.** No documented Bolna first-token/stream maximum or keepalive contract was found. Events also wait for generation to end, so event injection cannot be assumed to rescue a request held open indefinitely. [Stream contract](https://www.bolna.ai/docs/customizations/using-custom-llm.md), [safe-point queue](https://www.bolna.ai/docs/graph-agent/event-injection.md)
3. **Graph prompt repeats injected text:** Events add a pending text property and a node asks a hosted model to read it verbatim. This may be useful for a preliminary experiment but preserves an avoidable rewriting/hallucination step; validate every critical date, time, number and negation. [Prompt substitution](https://www.bolna.ai/docs/graph-agent/event-injection.md)
4. **Fixed phrase bank:** Useful as a real, explicitly bounded fallback demonstration or hold instruction. It can use static cache, but cannot substitute for demonstrating dynamic sign-to-speech. [Static cache scope](https://www.bolna.ai/docs/graph-agent/static-nodes.md)

The source-backed promising direction is **app-controlled content with Bolna carrying the hearing person's call leg**. Bolna should not independently accept appointments while the signer is deciding. That control is a product requirement to validate through the adapter, not a documented default of a voice-agent platform. [Pipeline behavior](https://www.bolna.ai/docs/concepts/call-flow.md)

#### Gaps

- No dedicated arbitrary runtime exact-speak REST endpoint was found in the inspected current index, custom LLM, SDK, graph/event and calling references. This is a bounded search result, not a proof of global nonexistence. Ask Bolna whether a newer public/beta text-input or text-only relay mode exists. [Index inspected](https://www.bolna.ai/docs/llms.txt)
- The custom-LLM documentation establishes `messages` and protocol, but not the exact request headers/body containing execution/call metadata, the final-vs-partial transcript behavior, or task markers used for internal checks. Capture a redacted actual request before defining the adapter interface. [Contract](https://www.bolna.ai/docs/customizations/using-custom-llm.md)
- No stable live partial-ASR consumer websocket/SSE/transcript-event API was established. Custom endpoint turn-level captions are a credible inference; token-progress captions may need additional Bolna support or carrier media access. [SDK reference](https://www.bolna.ai/docs/developer-resources/sdks/web-call-api.md), [webhooks](https://www.bolna.ai/docs/post-call/polling-call-status-webhooks.md)
- Self-transitions and repeated same-node event speech are not specified. Do not assume a self-loop re-enters and speaks. Two alternating nodes are a candidate experiment, not a proven workaround. [Event behavior](https://www.bolna.ai/docs/graph-agent/event-injection.md)
- Event acknowledgment, cancellation, idempotency, duplicate behavior, TTL and reliable per-utterance playback-complete events remain unspecified. These matter if a user corrects a message while it is queued. [Event reference](https://www.bolna.ai/docs/graph-agent/event-injection.md)

#### Inferences (superseded proposals, not recommendations)

- Familiar workflow can mean the user chooses a contact, presses Call, signs, reads captions and hangs up in Ishara while the recipient receives a regular call. It should be approved as the user's relay instruction, and tested, not framed as a universal accessibility preference. [Adjustable online detection](https://www.bolna.ai/docs/agent-setup/engine-tab.md)

- Account credit/tier, destination verification/country, feature enablement, actual configured timers and carrier caller ID are uninspected. User readiness is useful evidence of access availability, not proof of each operational property.
- No legal assertion is made that all possible automated calling/recording uses are permissible. For the immediate experiment, use a consenting teammate and synthetic appointment data, agree whether recording is enabled, and do not call a real clinic. Wider jurisdictional questions remain outside the evidence gathered here.


## 3. Validation preserving native calls and actual buildathon constraints

### Takeaway

The first device proof is **native Phone call from own number + app speech injection**, then camera and system-caption coexistence. Bolna fitting inside that workflow is a separate gate. No telephony number purchase, forwarding or service-originated clinic call is required. Read-only account access does not authorize inference/session creation or prove media routing.

### Cited findings: hackathon

Official event: October 15–November 20, 2026; submission October 31, shortlist November 3, interviews November 5–7, results November 8, finale November 20 at Symphony in Bengaluru. Top three travel; top ten get tickets. Page says any idea with a voice component qualifies, including voice on an existing product; registration offers solo/teams two/three/four. **Retrieved page does not explicitly establish mandatory Bolna use**, minimum integration, deadline timezone, submission assets/video length/repository requirements or judging weights. Confirm actual organizer rules rather than infer sponsorship requirements. [Official buildathon page](https://www.bolna.ai/symphony/buildathon/)

### Inferences: non-code experiment procedure, not executed

1. Freeze outcome: normal outgoing Phone call, own existing number, recipient sees normal identity, no additional service call. Obtain consenting teammate, exact iOS version on iPhone17, agreed duration/recording. Verified Bolna test number is irrelevant.
2. After experiment implementation is authorized, test approved harmless fixed local speech through Apple-supported injection. Confirm **remote** hearing, not just local playback, while native call persists. Camera/model/cloud TTS can wait until this route is proved.
3. Test signing camera, foreground/background transitions, audio route changes, interruption and cleanup. Measure camera survival and speech route; Apple-specific report defines APIs/entitlements. Device evidence determines compatibility.
4. Determine usable caption placement alongside signing. Distinguish system-visible Live Captions from application-readable transcripts. Bolna webhooks/custom LLM cannot transcribe native remote audio they never receive.
