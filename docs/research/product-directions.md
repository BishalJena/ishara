# Build accessible calls around user control

Synthesis updated 19 October 2026 from source research checked 18 October. Research only; no implementation or calls performed.

**Bet on one user-controlled administrative appointment call, demonstrated seated with a propped iPhone, including a changed offer and a genuine correction.** Preserve the preferred ordinary own-number Phone workflow if a short Bolna/audio/device proof succeeds; otherwise make an explicit pivot to an app-owned Bolna call for the same task. Meaningful Bolna integration is now mandatory by founder instruction, and researching deviations is authorized; implementation remains paused. This direction combines a familiar human goal, visible user agency, and a bounded demonstration without claiming universal ISL translation. Pickup coordination has stronger specific problem evidence, but outdoor signing posture makes it a weaker first physical demo. No complete transport, recognizer, phone interaction or Deaf-user experience has been validated. These are research-backed product judgments, not an official judging rubric or predicted winning odds.

## An everyday task matters more than vocabulary size

The opportunity is a necessary voice conversation the user wants to conduct without recruiting someone else. An Indian study of **15 interviews and 131 survey responses**, with data collected in 2022 among employed DHH adults, describes service-provider calls, ride/delivery coordination, failed text exchanges and dependence on hearing intermediaries. It also identifies privacy, agency, caption-reading pace and language problems. This supports a concrete access hypothesis, not a claim about every Deaf adult or current platform behavior. ([Primary study](https://roshni-poddar.github.io/assets/pdf/interact23a-sub1087-cam-i7.pdf))

Existing alternatives constrain the pitch. SignAble advertises human ISL video interpretation and relay calls to ordinary phones; ISLRTC announced VRS integration into helpline 14456. Uber documents accessibility messaging features. Ishara must show a useful bounded signed exchange and repair, rather than claim to invent relay or make text/interpreters obsolete. Captions address incoming speech; the proposed value is the user's ability to initiate, disagree and correct through supported signing. ([SignAble](https://signable.live/for-individuals-communicate-with-the-deaf/), [ISLRTC announcement](https://www.pib.gov.in/PressReleseDetailm.aspx?PRID=2098822), [Uber](https://www.uber.com/us/en/newsroom/globalaccessibilityawarenessday2024/))

The initial demonstration should use a familiar clinic's **administrative scheduling**, excluding medical advice or consent. Choose contact, request an appointment, read the actual reply, refuse an unsuitable slot, propose an approved alternative and deliberately confirm. The hearing counterpart chooses between alternatives during the demonstration. Include an uncertain input that remains silent until repaired. This shows communication agency, not a memorized recognition recital. Saved details/pickers can supply explicit dates or names, but their role must remain visible.

Pickup remains a compelling future task: a driver is at the wrong entrance and the user corrects the location. However, carrying bags, sunlight, urgency and no available phone surface undermine hands-free framing and caption reading. A desk appointment call makes a propped phone plausible without establishing sidewalk usability. Signing includes hands, face and body; even the seated arrangement needs evaluation at a distance where captions remain legible. No Deaf participant has reviewed either scenario. ([W3C signing guidance](https://www.w3.org/WAI/media/av/sign-languages/), [WFD AI guidance](https://wfdeaf.org/artificial-intelligence-and-sign-languages/))

## Four concrete directions trade familiarity against media control

The comparison is engineering judgment, not measured user preference. All four depend on unproven sign recognition and readable return language. Choosing one does not authorize building the others.

| Direction | Normal user steps and honest demonstration | Bolna's essential role | Main compromise |
|---|---|---|---|
| **Own-number appointment conversation — preferred first bet** | Call normally → open/prop Ishara → sign/read system captions → reject changed slot → correct → confirm → native hangup | Patched OSS session carries approved outgoing content, streamed speech, ordering, cancellation, voice/language and deliberate pauses | Bolna cannot hear the native call; combined device path and substantive integration unproved |
| **App-owned accessible call — conditional pivot** | Contact → Call in Ishara → sign/read actual returned turns → correct offer → hang up in app | Hosted remote ASR/TTS, call lifecycle, tools/events and controlled user-led speech | Different origination/caller identity; app return channel and approval loop need engineering |
| **Signed everyday errands — distinct alternative** | Sign “ask repair shop when ready” → approve request → agent calls → user approves changed proposal → receive result | Agent conducts factual conversation, publishes offers, waits for authority and reports outcome | Delegation rather than personal live interpreting; risk of generic assistant with sign launcher |
| **Counter exchange/check-in — distinct alternative** | Open/prop phone at counter → sign request → employee speaks → read reply → correct “exchange, not refund” | Mixed signed-text/audio orchestration, hearing-side ASR, faithful speech, pause/cancellation policy | Needs microphone/ASR caption tee, echo handling, private usable counter space; no runtime proof |

The supervised errand is strongest when the difference is accessible control: a repair shop says “after six, not four”; Bolna publishes that actual proposal and waits for a deliberate response. An unavailable appointment is a valid outcome. Calendar tooling only works for a connected business; arbitrary clinics do not become integrated calendars. The counter version keeps both people in their existing interaction and owns its microphone, but ASR self-echo and mixed input remain substantial work. Neither is automatically simpler merely because native Phone restrictions disappear. ([Bolna tools](https://www.bolna.ai/docs/graph-agent/tools-and-rag.md), [calendar integration](https://www.bolna.ai/docs/tool-calling/book-calendar-slots))

**The strongest counterargument to the primary bet is Bolna centrality.** Native calling leaves incoming understanding to the user and system captions; local TTS could explain a superficial version. The integration earns its place only if Bolna visibly manages faithful streamed delivery, changed pending output, pauses, cancellation and voice policy. If it is a redundant hop for canned audio, choose the explicit app-owned call, where removing Bolna removes the conversation medium. Hosted calling offers documented primitives, but its live app supervision still needs proof; documentation cannot establish that its total effort is lower.

## New source evidence makes native Bolna engineerable, not ready

The earlier hosted standalone-TTS search was too narrow to establish all integration possibilities. Pinned Bolna OSS source accepts text/audio packets and emits base64 audio, marks and clear messages. A custom server can connect approved text to synthesis and a native consumer. This preserves the existing call without inventing a hosted endpoint. However, the inspected text handler routes into an LLM queue and uses the audio input route; issue #898 documents a related routing defect. Task-manager turn-based/synthesizer lifecycle assumptions need adaptation too. **This is a source-extension project, not a parameter update.** ([Pinned input](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/input_handlers/default.py), [output](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/output_handlers/default.py), [task manager](https://github.com/bolna-ai/bolna/blob/38faa409b3e425b582573eaf0c5e8c3e0d2bda5e/bolna/agent_manager/task_manager.py), [issue](https://github.com/bolna-ai/bolna/issues/898))

Apple supports AAC speech into existing calls, but simultaneous camera, speech injection and system captions remain untested on the iPhone 17's unknown installed iOS. Ishara cannot read unrelated incoming Phone audio; a model cannot extract an offered time from captions only the user sees. Native mute also mutes injection. English (India) captions do not establish Hindi translation. No upgrade recommendation follows without inspecting the actual device and supported languages. ([Apple AAC sample](https://developer.apple.com/documentation/avfaudio/adding-synthesized-speech-to-calls), [audio boundary](https://developer.apple.com/forums/thread/841340), [caption availability](https://www.apple.com/in/ios/feature-availability/#accessibility-live-captions))

For hosted calls, graph HTTP tools can publish a structured offer, and events can carry the user's authorized response. Publication is not delivery: events can queue during speech/generation, and proactive output can be skipped while the recipient speaks. Custom LLM streaming supports a deterministic approved-content adapter, but exact task/session correlation, timing and repetition need validation. Structured offers must be labeled interpreted offers, not verbatim captions. Static audio is generated at save time, so cached latency is not fresh sign-to-speech latency. ([Events](https://www.bolna.ai/docs/graph-agent/event-injection.md), [custom LLM](https://www.bolna.ai/docs/customizations/using-custom-llm.md), [static nodes](https://www.bolna.ai/docs/graph-agent/static-nodes.md))

A small task-specific recognizer is more defensible than promising continuous translation. The inspected 263-label INCLUDE map has useful location/time concepts but lacks WAIT, REPEAT, YES/NO and number classes. This is a checkpoint coverage gap, not proof those concepts lack ISL signs or other datasets. Real pretrained INCLUDE/OpenHands paths exist, although binaries/runtime compatibility were not exercised and OpenHands is no longer actively maintained. Phrase datasets exist; exact task coverage, rights and naturalness need auditing. Jev image verification is an experimental comparator, not established ISL accuracy; added models must reduce wrong speech or repair burden. ([Label map](https://raw.githubusercontent.com/AI4Bharat/INCLUDE/master/label_maps/label_map_include.json), [INCLUDE](https://github.com/AI4Bharat/INCLUDE), [OpenHands](https://github.com/AI4Bharat/OpenHands), [iSign](https://exploration-lab.github.io/iSign/), [Jev images](https://docs.typesafe.ai/images))

## Two experiments decide the next phase

**Experiment one is the complete voice-interface proof**, once implementation and a consensual call are authorized. Feed known approved content through actual Bolna OSS output into the existing Phone call while the camera and supported system captions operate. Then change/cancel a pending phrase and pause before a second turn. Record remote audibility, exact content, interruption and duplicate/stale speech. A proposed initial two-day implementation window prevents polishing around unresolved transport. If this cannot work, test the explicitly different hosted call: an actual counterpart offer must reach the app, and a changed authorized response must affect that same call without autonomous acceptance. Neither branch passes on a local speaker demo or event acknowledgment alone.

**Experiment two is a blinded bounded conversation with repair.** Audit the required source-qualified signs/phrases first, then compare a real temporal baseline and optional Jev verification against supported turns, unknown/idle input, partial framing and negation/correction. Include a different recording session and competent held-out signer where obtainable; disclose when that evidence is unavailable. Have the counterpart choose a changed slot live. Measure wrong automatically spoken utterances, confirmations/re-signs, duplicates and signer-finish-to-remote-audio latency including commitment delay. Speech already heard cannot be undone. No numeric acceptance threshold or model runtime result exists yet; agree thresholds before testing rather than retrofit success.

These experiments should produce one conversation map with normal, changed-offer, refusal and failure branches; a licensed phrase/data manifest; supported spoken/readable languages; and an evidence-backed transport decision. Requirements then specify semantic authority and acceptance behavior; architecture defines media ownership, interfaces and state; tickets allocate the measured remaining work. The current source research does not authorize those builds, and the team should not outsource technical investigation to the founder.

## Conclusion

The official page gives **31 October** submission and a voice-component theme, but no retrieved scoring weights or precise timezone. Meaningful Bolna is mandatory because the founder confirmed it; hosted-only versus OSS eligibility still needs organizer clarification. There is no defensible winning probability. ([Official buildathon](https://www.bolna.ai/symphony/buildathon))

The competitive story is a person retaining control when a real conversation changes direction. Lead with the seated appointment task, preserve ordinary calling if the substantive Bolna/device proof works, and disclose an app-owned call pivot if it does not. A narrow working exchange with visible abstention and correction is more credible than several modes whose central interaction has never run.
