## 3. What D9 needs from Bolna

| D9 piece | How the code does it | Bolna side today | Change needed |
|---|---|---|---|
| **Opening right after `in-progress`** | The status webhook moves the call to `in_call`; the backend then sends the opening ("I'd like to book a doctor's appointment for …") as a `user_reply` event, turn `delegate-open` | Webhook set; `user_reply` edge on `listen` exists. Events wait while the disclosure plays (documented) | **Yes, recommended:** turn on "Ignore user speech before welcome message". See the risk below |
| **Custom-LLM listen node** | On each receptionist turn the `listen` request reaches our endpoint, which answers with the delegate's line (Groq brain, rules as fallback, every line through `check_line`) | Matches: `listen` is an LLM node on our custom model; `repeat_after_silence_seconds` 15 (delegated calls answer `[silence]` with nothing) | None |
| **Status webhook** | `/bolna/webhook/<secret>`; `in-progress` → in call, `completed`/`no-answer`/… → ended | Set, all statuses | None |
| **Call summary** | `ExecutionUpdate.summary` from the final webhook goes into the notes as `bolna_summary` | **Off** (`call_summary_enabled: false`) | **Yes:** set `call_summary_enabled: true` |
| Hang-up after a settled brief | 6 s after the closing/callback line, the backend sends `end_call` → static goodbye node | Matches | None |

**Risk found by reading the code (to watch on the first D9 call, not proven live):**

1. The receptionist usually says "Hello?" when they pick up. With the agent-level interrupt
   threshold at 1 word, that cuts the disclosure, and the same words reach our `listen`
   node. `delegate_reply` does not check whether the opening is still in flight, so the
   brain may answer "Hello?" with its own line **and** the buffered opening event may then
   speak too: a possible double line at the start of every D9 call. Ignoring speech until
   the disclosure has finished removes the trigger on Bolna's side.
2. The opening's 10 s delivery timer starts when the opening is sent (at `in-progress`),
   while Bolna is still playing the ~7 s disclosure. If Bolna asks our endpoint for the
   speak node after 10 s, the turn is already marked not delivered and the backend refuses
   it, so the opening is silently dropped. Watch the time from `in-progress` to `spoken` for
   `delegate-open` on the first call.
3. If either shows up live, the fix is in `backend/app/calls.py` (another task is hardening
   `backend/app` right now), done as its own commit with a regression test.

**Exact agent changes proposed** (both need the Gate 1 go):

- `agent_config.call_summary_enabled = true` (documented on the create/update/PATCH API).
- `tasks[0].task_config.discard_pre_welcome_utterance = true`. This name comes from the
  live GET; the create API schema does not list it, only the dashboard toggle
  ("Ignore user speech before welcome message") is documented. So: add it to the payload,
  PUT, then GET to confirm it stuck; if Bolna ignores it, flip the dashboard toggle and GET
  again.
- Both go into `build_agent_payload()` (`backend/app/bolna_agent.py`) and the regenerated
  `agent.json`, because `update` is a full PUT that would otherwise reset them.
- Not proposed: raising the agent-level interrupt threshold. It would also make the
  delegate's listen-node lines harder for the receptionist to interrupt; decide after the
  first call.

Doc drift spotted: the call-summary claim (ledger B29, the comment in
`backend/app/bolna_status.py`) says the summary "runs on every call". The current Bolna
API docs and changelog say it is an agent toggle, off by default, and the live agent has it
off. The migration page still has the older wording.
